# Hard Mentor — менторки, материалы и обращения

Telegram-бот программы Hard Mentor (AITU): расписание менторок, входные билеты,
самооценка по чек-листам, банк PDF/DOCX, посещаемость и отдельный раздел обращений.
Python 3.12 · aiogram 3 · PostgreSQL · деплой на Railway (long polling, один worker).

## Новое в этой версии

**Обновление уже работающего бота: [MENTORING_GUIDE.md](MENTORING_GUIDE.md).**
Создание занятия — `/newsession` (координатор), запись — `/sessions`, банк — `/materials`,
чек-лист темы — `/setchecklist`, файл в банк — `/addmaterial`, сводка — `/sessionreport`.
Всё доступно также через кнопки раздела «Менторки». Готовое расписание в код не зашито.

Массовые `/addmentor` и `/delmentor`, SQL-импорт и отдельная таблица `mentors` сохранены.
Новых обязательных Variables нет. При старте добавляются только отсутствующие таблицы.

Список изменений: [CHANGES_MENTORING.md](CHANGES_MENTORING.md).

## Деплой на Railway

1. **Бот.** В @BotFather: `/newbot` → сохраните токен.
2. **Репозиторий.** Залейте эту папку в GitHub (файл `.env` в репозиторий не попадает — он в `.gitignore`).
3. **Проект.** Railway → New Project → Deploy from GitHub repo → выберите репозиторий.
   Railway сам найдёт `Dockerfile` и `railway.json`.
4. **База.** В том же проекте: `+ New` → Database → PostgreSQL.
5. **Переменные** сервиса бота (вкладка Variables):

   | Переменная | Значение |
   |---|---|
   | `BOT_TOKEN` | токен из BotFather |
   | `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` — ссылка на базу из п. 4 |
   | `COORDINATOR_IDS` | Telegram ID координатора (несколько — через запятую) |
   | `LEAD_IDS` | Telegram ID руководителя программы |

   Остальные (`LEAD_GETS_ALL`, `DAILY_LIMIT`, `TIMEZONE`, `REPORT_WEEKDAY`, `REPORT_HOUR`,
   `SECRET_KEY`) необязательны — см. `env.example`.
6. **Узнать ID.** Первый деплой можно сделать без `COORDINATOR_IDS`/`LEAD_IDS`: координатор и
   руководитель пишут боту `/myid`, вы вносите числа в Variables, Railway передеплоит сам.
   Оба должны нажать `/start` — иначе Telegram не даст боту писать им первым.
7. **Менторы.** Менторы нажимают `/start`, координатор или руководитель отправляет
   `/addmentor @username1 @username2 123456789` — сразу весь список. Можно отправить UTF-8 `.txt`
   с подписью `/addmentor` (до 1000 записей, 128 КиБ). Удаление: `/delmentor` в том же формате.
   Подробно: [MENTOR_IMPORT_GUIDE.md](MENTOR_IMPORT_GUIDE.md).

При запуске создаются отсутствующие таблицы. Старые записи `users.role = 'mentor'`
однократно переносятся в `mentors`. Поле `users.role` оставлено только для совместимости;
текущую принадлежность к менторам определяет **только таблица `mentors`**.
Статус переноса хранится в `meta` (`schema:mentors:v1`), поэтому удалённые менторы
не возвращаются после перезапуска. Не удаляйте этот маркер. Домен, порт и healthcheck не нужны: бот сам ходит в Telegram.

### Что важно знать про Railway

- **Одна реплика.** Два процесса с одним токеном дерутся за `getUpdates`. В `railway.json` стоит
  `numReplicas: 1` и `overlapSeconds: 0`, чтобы при редеплое старый контейнер гасился до запуска
  нового. Если в логах всё же мелькнёт `TelegramConflictError` на пару секунд — это редеплой, aiogram
  переподключится сам.
- **Диск эфемерный.** Всё постоянное лежит в Postgres, файлы не сохраняются вообще (вложения — это
  `file_id` Telegram).
- **Незавершённые анкеты живут в памяти.** Редеплой посреди заполнения = человек получит
  «кнопка устарела, начните заново». Отправленные обращения и входные билеты не теряются;
  уже нажатые ответы чек-листа также сохранены в БД. Сообщения, пришедшие во
  время редеплоя, бот обработает после старта.
- **Логи видны всем участникам проекта Railway.** Бот не пишет в логи ID заявителей — только номер
  и категорию обращения. Не добавляйте `print(message)` при отладке на проде.
- **Стоимость.** Проверяйте актуальные условия и потребление в своём кабинете Railway;
  фиксированная цена работы бота не гарантируется.

### Роли в разделе обращений

| Роль | Как получить | Что может |
|---|---|---|
| Mentee | любой, кто написал боту | подать обращение, смотреть свои, дополнять, оценивать |
| Mentor | запись в `mentors`: `/addmentor`, импорт `.txt` или SQL | видит **только назначенные ему** тикеты; отвечает, меняет статус |
| Coordinator | `COORDINATOR_IDS` | вся очередь, кроме тикетов «только руководителю» |
| Program Lead | `LEAD_IDS` | всё, включая жалобы на координатора; эскалации и сводка |

Роли координатора и руководителя задаются **только** переменными окружения — командой в чате их
не получить. Приоритет: `LEAD_IDS` → `COORDINATOR_IDS` → `mentors` → обычный пользователь.
Наличие у руководителя значения `mentee` в старой колонке `users.role` не ограничивает его права.

Массовые команды возвращают сводку и `mentors_result.txt`, но не рассылают сотни уведомлений.
Одиночное изменение отправляет уведомление пользователю. Уже добавленные записи и повторы
пропускаются. Неизвестные, некорректные и неоднозначные usernames перечисляются в отчёте.
`/mentors` и кнопки выбора/назначения имеют страницы — все менторы доступны, не только первые 20/30.

### Маршрутизация

| Обращение | Кому уходит |
|---|---|
| Вопрос, жалоба, предложение | координатор и руководитель по умолчанию; `LEAD_GETS_ALL=false` отключает обычные уведомления руководителю |
| Благодарность с выбранным ментором | сразу ментору, тикет закрыт; координатору и, при `LEAD_GETS_ALL=true`, руководителю — копия |
| Серьёзное сообщение | координатор **и** руководитель, с пометкой СРОЧНО |
| «Это про координатора» (жалоба или серьёзное) | **только** руководитель; координатор не видит тикет ни в очереди, ни по номеру, ни в сводке |

Просроченный SLA (нет первого ответа за 4/24/48 ч) — разовое напоминание ответственному и
руководителю. Проверка каждые 10 минут.

### Анонимность (разделы 6.2 и 12 спека)

- У анонимного тикета `submitter_id` и `submitter_name` = `NULL`. Это обеспечивает
  `repo.create_ticket`, а не хэндлер — ошибка в сценарии не приведёт к утечке.
- Время создания округляется до часа; у пользователей в БД нет отметок времени вообще.
- Дневной лимит считается **в памяти процесса**: на диск не попадает, с тикетами не связан.
- Вложения отправляются команде по `file_id`, а не пересылкой (пересылка показала бы автора).
- В логах нет ID заявителей — на это есть тест.
- Вместо уведомлений аноним получает **секретный код** (`/status HM-0042 ABCD-EFGH`): по нему видны
  статус и ответы, можно дополнить обращение и поставить оценку. В БД хранится только HMAC кода.
  10 неверных попыток в день — и ввод блокируется.
- Остаточный риск, который код не закрывает: координатор получает уведомление в реальном времени, и
  если в пилоте 5 человек, автора можно угадать по стилю и обстоятельствам. Это вопрос регламента
  конфиденциальности (раздел 12), а не бота.

Проверка: `pytest -k "anonymous or logs"`.

## Отступления от спека — осознанные

- **Postgres сразу, без Google Sheets.** На Railway это один клик, а очередь координатора сделана
  прямо в Telegram (`/queue` с фильтрами, карточка с кнопками). Таблицу пришлось бы синхронизировать.
- **Добавлено:** код доступа для анонимных тикетов; «✏️ Дополнить» — заявитель может ответить на
  уточняющий вопрос; вопрос «касается ли координатора» в серьёзных сообщениях; напоминания о
  просрочке SLA.
- **Не сделано (Phase 2 по спеку):** автоответ на FAQ через regulations-бот; веб-дашборд.
- **Не сделано, стоит решить рабочей группе:**
  - Руководитель сейчас **не** read-only — ему нужны кнопки, чтобы разбирать жалобы на координатора.
  - Архивация в конце учебного года не автоматизирована (данные просто лежат в Postgres).
  - Казахский язык: добавляется ключом `"kk"` в `texts.py` и в `detect_lang`.
  - Поле `cohort` в `users` есть, но бот его не спрашивает.

## Локальный запуск и тесты

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
pytest                                   # SQLite в памяти, сеть не нужна
TEST_DATABASE_URL=postgresql://postgres@localhost/hm_test pytest   # то же на Postgres

cp env.example .env                     # заполнить BOT_TOKEN и DATABASE_URL
set -a; source .env; set +a
python -m bot
```

Не запускайте локально бота с **тем же токеном**, что на Railway, — они будут перехватывать
сообщения друг у друга. Для разработки заведите второго бота.

**Внимание:** `TEST_DATABASE_URL` должен указывать только на отдельную тестовую БД: тесты очищают все таблицы. Не используйте рабочую базу Railway.

Результат проверок этой версии и ограничения среды: [VALIDATION_MENTORS.md](VALIDATION_MENTORS.md).

Тесты прогоняют настоящие хэндлеры через фейковую сессию Telegram, которая заодно проверяет то,
за что реальный API вернул бы 400: битый HTML, длину текста и `callback_data`.


### Уведомления о новых тикетах

Новые обращения `/feedback` создаются вместе с заданиями доставки в `ticket_notifications`
в одной транзакции. Бот сразу отправляет карточку с кнопкой открытия обращения;
при временных сбоях очередь повторяет отправку, в том числе после перезапуска.
Проверка очереди каждые 10 секунд. Жалобы на координатора доступны только руководителям.
`/testnotify` проверяет личные уведомления сотрудника, показывает правило получения
тикетов и повторяет только его неотправленные уведомления.

Если в Railway уже стоит `LEAD_GETS_ALL=false`, поменяйте на `true`, чтобы руководители
получали все новые обращения. Новых обязательных переменных нет.
Подробнее: `TICKET_NOTIFICATIONS_GUIDE.md`; проверки и ограничения —
`VALIDATION_TICKET_NOTIFICATIONS.md`.
