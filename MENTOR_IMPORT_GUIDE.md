# Менторы: обновление Railway и массовое добавление

## Обновить существующий бот

1. Сохраните резервную копию текущей базы перед обновлением.
2. Замените файлы проекта файлами из архива, закоммитьте и отправьте в подключённый к Railway репозиторий. Не создавайте новый Postgres и не удаляйте старые таблицы.
3. Переменные `BOT_TOKEN`, `DATABASE_URL`, `SECRET_KEY`, `COORDINATOR_IDS` и `LEAD_IDS` оставьте прежними. Новых обязательных переменных нет.
4. Выполните деплой сервиса бота. При старте он сам создаст `mentors` и один раз перенесёт старых менторов из `users.role`. Обращения, заметки, пользователи и коды доступа не переписываются.
5. В боте от имени координатора/руководителя выполните `/mentors`. В БД появится таблица `mentors` с единственной колонкой `telegram_id`.

`users.role` — устаревшая колонка, оставленная для совместимости с существующей схемой. Её не нужно редактировать или удалять вручную. Даже значение `mentor` в этой колонке после миграции **не даёт прав**. Роль руководства по-прежнему задаётся через Variables.

Однократность миграции фиксируется ключом `schema:mentors:v1` в таблице `meta`. Не удаляйте его: повторный импорт старой колонки мог бы вернуть ранее удалённых менторов. Не возвращайте старую версию кода без отдельного плана отката: она не читает новую таблицу.

## Вариант 1 — одним сообщением

Люди уже должны быть в `users` (например, нажали `/start`). Telegram ID — ID пользователя, не номер телефона.

```text
/addmentor
@mentor_one
@mentor_two
123456789
```

Можно разделять записи пробелами, переводами строк, запятыми и точками с запятой; смешивать usernames, ID и ссылки вида `https://t.me/mentor_one`. Регистр usernames не важен. Имя без `@` тоже принимается.

```text
/addmentor @mentor_one, @mentor_two; 123456789
```

Сводка покажет, сколько добавлено, сколько уже были менторами, какие записи не найдены или имеют неправильный формат. Повторы не создают новых строк и повторных уведомлений. При массовой операции бот прикладывает полный `mentors_result.txt`.

Если в базе оказался один username у нескольких пользователей, бот не выбирает первого наугад: такие записи пропускаются с пометкой «неоднозначные», используйте числовой ID. Бот знает usernames только на момент последнего взаимодействия пользователя; при сомнениях используйте ID. Новых пользователей по неизвестным ID/username эта версия не создаёт.

## Вариант 2 — текстовый файл

Создайте `mentors.txt` в UTF-8 (допускается BOM). Каждая строка — ID или @username, без шапки таблицы, ФИО и нумерации.

```text
@mentor_one
@mentor_two
123456789
```

Отправьте файл боту, в подписи напишите `/addmentor`. Другой способ: отправьте `.txt`, затем ответьте на сообщение с файлом командой `/addmentor`.

Лимиты одной операции: 1000 записей, 128 КиБ. XLSX/CSV не обрабатываются — сохраните один столбец в обычный `.txt`. Превышение лимита, неподходящий формат или ошибка скачивания не меняют список менторов.

Массовое изменение проходит **без индивидуальной рассылки**. Участники получат новые права при следующем взаимодействии; `/start` обновляет кнопки меню. Одиночное добавление/удаление сохраняет уведомление пользователю. Ошибка доставки уведомления не отменяет сохранённые права.

## Удалить несколько менторов

```text
/delmentor @mentor_one @mentor_two 123456789
```

Также поддерживается `.txt` с подписью `/delmentor` или команда в ответ на файл. `/addmentors` и `/delmentors` — дополнительные варианты тех же команд.

Удаляется только принадлежность к менторам: пользователь и история обращений остаются. При удалении командой активные назначения обычного ментора возвращаются в общую очередь. Права и назначения руководителей/координаторов из Variables не снимаются.

После удаления через SQL исторические `assigned_to` могут остаться в базе; новые уведомления проверяют актуальные права и при необходимости направляются руководству. Доступ к старым кнопкам также проверяет текущую таблицу `mentors`. Координатор может переназначить открытые обращения.

## Вариант 3 — напрямую через PostgreSQL

Сначала выполните деплой новой версии, чтобы таблица появилась. Не создавайте её вместо миграции вручную.

Проверка:

```sql
SELECT u.telegram_id, u.display_name, u.username
FROM mentors AS m
JOIN users AS u ON u.telegram_id = m.telegram_id
ORDER BY lower(u.display_name), u.telegram_id;
```

Добавление по ID уже зарегистрированных пользователей:

```sql
INSERT INTO mentors (telegram_id)
VALUES (123456789), (987654321)
ON CONFLICT (telegram_id) DO NOTHING;
```

При неверном/незарегистрированном ID сработает внешний ключ: строка не добавится. Для массового добавления по usernames с отчётом используйте `sql/bulk_add_mentors.sql`: замените примеры в `VALUES`. Он пропускает ненайденные и неоднозначные usernames, не создаёт дубликаты, показывает результат для каждого имени.

Удаление по ID:

```sql
DELETE FROM mentors
WHERE telegram_id IN (123456789, 987654321)
RETURNING telegram_id;
```

SQL-изменения не отправляют уведомлений и не требуют перезапуска бота. Не обновляйте `users.role`: актуальные проверки эту колонку игнорируют.

Railway позволяет просматривать и редактировать строки таблиц через Database View. Для SQL-скриптов можно использовать подключённый PostgreSQL-клиент (например, psql, pgAdmin или DBeaver). Не публикуйте `DATABASE_URL` и пароль базы.

Официальная документация Railway: https://docs.railway.com/databases/database-view и https://docs.railway.com/cli/connect .

## Проверка после деплоя

Выполните `/addmentor` с двумя тестовыми зарегистрированными пользователями, затем `/mentors`. Повторите добавление — строки не должны дублироваться. Удалите одного, повторно выполните `/mentors` и перезапустите бот: удалённый не должен вернуться. У обычного ментора `/queue` показывает только назначенные ему обращения; админские команды ему недоступны. Координатор и руководитель сохраняют свои права из Variables.

Для разработчика: `pip install -r requirements-dev.txt` и `pytest`. Тестовый `TEST_DATABASE_URL` должен указывать только на отдельную тестовую БД: сквозные тесты очищают все таблицы. Никогда не запускайте их против рабочей Railway-базы.
