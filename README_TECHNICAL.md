# Hard Mentor Bot

Telegram-бот для организации менторок и обработки обращений студентов. Объединяет расписание, запись на занятия, подготовку по чек-листам, банк материалов, посещаемость и очередь тикетов с уведомлениями для команды.

**Python 3.12 · aiogram 3 · SQLAlchemy 2 · PostgreSQL · Docker · Railway**

В проекте два независимых сценария: **входной билет** — запись студента на занятие с вопросом и самооценкой; **тикет** — вопрос, предложение, благодарность или жалоба через `/feedback`. Входные билеты не анонимны. Для тикетов предусмотрен отдельный анонимный режим.

<a id="features"></a>
## Возможности

### Менторки и подготовка

Координатор создаёт занятие: выбирает или добавляет предмет и тему, назначает ментора, указывает дату, время, длительность и место либо ссылку на встречу. Руководитель также может управлять расписанием. Ментор самостоятельно занятия не создаёт.

Студент выбирает **предмет → тему → занятие → отправляет вопрос → получает рекап-гайды → заполняет чек-лист**. Ответы по каждому пункту: «Понимаю», «Есть вопросы», «Не понимаю». Это самооценка, а не тест с правильными ответами.

Назначенный ментор и администрация видят участников, вопросы, индивидуальные ответы и сводку понимания тем. Ответы сохраняются по мере заполнения. Шаблон чек-листа фиксируется для занятия, поэтому последующее редактирование банка не переписывает уже собранные ответы. Отсутствие чек-листа или материалов не мешает записаться.

Координатор может перенести будущее занятие, сменить место или ведущего с сохранением записей. При изменениях участникам отправляются уведомления. Если за два часа до начала на занятие никто не записан, координатор и руководитель получают предупреждение. **Бот не отменяет занятия автоматически**: отмена выполняется администрацией с указанием причины и подтверждением.

Напоминания о незаполненном чек-листе запланированы за сутки и за два часа до начала. Они не отправляются после отмены занятия, снятия записи, заполнения чек-листа или начала занятия.

### Банк материалов и отчётность

Менторы, координаторы и руководители наполняют банк без предварительного согласования. Документы распределяются по предметам и темам; тип материала — рекап-гайд или материал занятия. Можно открыть документ студентам и команде либо оставить доступ только команде.

Принимаются **PDF и DOCX до 20 МиБ**, отправленные как документы, не как фотографии. Чек-лист содержит от 1 до 20 пунктов, до 110 символов на пункт.

После занятия ментор отмечает присутствовавших и отсутствовавших, завершает занятие и загружает материалы. Неотмеченные студенты не считаются отсутствовавшими автоматически; завершение требует заполненной посещаемости. При загрузке из карточки занятия предмет и тема подставляются автоматически.

`/sessionreport` формирует сводку **за всё время** и файл `mentoring_report.txt`: занятия, записи, посещаемость, заполнение чек-листов и наличие материалов. В выгрузке нет имён и вопросов студентов.

### Обращения студентов

Раздел `/feedback` поддерживает вопросы, предложения, благодарности, жалобы и серьёзные обращения. Можно приложить вложение, выбрать анонимную подачу, посмотреть статус, дополнить тикет и оценить решение. Команда работает с очередью, назначает ответственного, отвечает студенту, добавляет внутренние заметки и меняет статус.

У новых тикетов есть отдельные уведомления с кнопкой открытия карточки. Очередь доставки хранится в БД и повторяет отправку при временных ошибках. Жалобы на координатора доступны только руководству. По обращениям также предусмотрены недельная сводка и контроль срока первого ответа.

Реализация: [обработчики менторок](bot/handlers/mentoring.py), [правила занятий](bot/mentoring/service.py), [обращения](bot/handlers/feedback.py), [работа команды](bot/handlers/staff.py).

<a id="roles"></a>
## Роли и права

| Роль | Откуда берётся | Доступ |
|---|---|---|
| Студент — `mentee` | Пользователь без роли сотрудника | Расписание, свои записи, открытые материалы, собственные обращения |
| Ментор — `mentor` | Запись в таблице `mentors` | Свои назначенные занятия и тикеты, участники своих занятий, посещаемость, наполнение банка |
| Координатор — `coordinator` | Telegram ID в `COORDINATOR_IDS` | Управление менторами и всеми занятиями, сводки, очередь без тикетов «только руководителю» |
| Руководитель — `lead` | Telegram ID в `LEAD_IDS` | Административные функции и доступ к ограниченным обращениям, включая жалобы на координатора |

Приоритет определения роли:

```text
LEAD_IDS → COORDINATOR_IDS → таблица mentors → mentee
```

**`users` — справочник пользователей, а не источник актуальных прав.** Колонка `users.role` оставлена для совместимости со старой базой. Значение `mentee` в ней у руководителя или ментора не означает отсутствие прав. Не используйте `UPDATE users SET role = 'mentor'` для назначения роли в этой версии.

Списки руководства задаются только через переменные окружения. `/addmentor` и `/delmentor` не выдают и не отнимают административные права. Чтобы координатора или руководителя можно было выбрать ведущим занятия, его также нужно внести в `mentors`.

Проверка роли выполняется при взаимодействии с ботом. Изменения таблицы `mentors` учитываются без перезапуска; изменения Variables требуют нового запуска процесса.

Реализация: [config.py](bot/config.py), [middleware.py](bot/middleware.py), [repo.py](bot/repo.py).

<a id="railway"></a>
## Быстрый старт на Railway

### Первый запуск

1. Создайте бота через `/newbot` у **@BotFather** и сохраните токен. Загрузите проект в свой GitHub-репозиторий: `bot/`, `Dockerfile`, `railway.json` и `requirements.txt` должны находиться в корне выбранного исходного каталога.
2. Создайте сервис Railway из репозитория и добавьте PostgreSQL в тот же проект. Сборка проекта настроена через `Dockerfile`; он запускает `python -m bot`.
3. В **Variables сервиса бота** задайте параметры из примера ниже. В ссылке на БД `Postgres` — имя сервиса базы, а не фиксированное имя для любого проекта.
4. Примените изменения и выполните Deploy. Изменения Variables в Railway нужно подтвердить и развернуть — одного редактирования значений недостаточно.
5. Координатор, руководитель и менторы открывают личный чат с ботом и отправляют `/start`. Свой числовой Telegram ID можно узнать через `/myid`. После заполнения ID в Variables снова примените изменения. Затем добавьте менторов и проверьте `/testnotify`.

Пример для Variables — **значения токена и ID замените своими**:

```dotenv
BOT_TOKEN=YOUR_BOT_TOKEN
DATABASE_URL=${{Postgres.DATABASE_URL}}
COORDINATOR_IDS=111111111,222222222
LEAD_IDS=333333333
LEAD_GETS_ALL=true
TIMEZONE=Asia/Almaty
```

Для самого запуска обязательны только `BOT_TOKEN` и `DATABASE_URL`. Однако без настроенных сотрудников некому обрабатывать обращения и управлять занятиями. Список `LEAD_IDS` нужен для ограниченных тикетов и эскалаций.

Используется **long polling**, не веб-сервер: домен, публичный порт и HTTP healthcheck для сервиса бота не нужны. В [railway.json](railway.json) указаны одна реплика и `overlapSeconds: 0`. Не запускайте параллельно локальную и Railway-копию с одним токеном.

Справка платформ: [Variables Railway](https://docs.railway.com/variables), [Dockerfile Railway](https://docs.railway.com/builds/dockerfiles), [создание бота и начало диалога](https://core.telegram.org/bots#how-are-bots-different-from-users).

### Обновление работающего бота

Перед обновлением сохраните резервную копию PostgreSQL. Замените файлы репозитория содержимым папки проекта, сохранив рабочую базу и значения Variables. При запуске создаются отсутствующие таблицы, включая `mentors`, таблицы менторок и очереди уведомлений.

Пользователи со старым `users.role = 'mentor'` **однократно** переносятся в `mentors`. Маркер `schema:mentors:v1` в таблице `meta` предотвращает повторный перенос. Не удаляйте его: иначе старые значения могут повторно назначить уже снятые роли.

Если ранее было задано `LEAD_GETS_ALL=false`, смените его на `true`, когда руководителям нужны уведомления обо всех новых обычных тикетах. После обновления отправьте `/start` для обновления меню и `/testnotify` для проверки доставки.

Это создание недостающих таблиц и конкретная миграция менторов, **не универсальная система миграций схемы**. Для будущего изменения существующих колонок потребуется отдельная миграция. Код инициализации: [db.py](bot/db.py).

<a id="configuration"></a>
## Переменные окружения

Пример: [env.example](env.example). Код читает переменные окружения через `os.environ`; файл `.env` автоматически не загружается.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BOT_TOKEN` | Нет, обязательна | Токен Telegram-бота |
| `DATABASE_URL` | Нет, обязательна | Подключение к PostgreSQL |
| `COORDINATOR_IDS` | Пусто | Числовые Telegram ID координаторов через запятую |
| `LEAD_IDS` | Пусто | Числовые Telegram ID руководителей через запятую |
| `LEAD_GETS_ALL` | `true` | Получает ли руководство также обычные новые обращения |
| `DAILY_LIMIT` | `5` | Дневной лимит отправки обращений одним пользователем |
| `TIMEZONE` | `Asia/Almaty` | Часовой пояс отображения расписания и времени отчётов |
| `REPORT_WEEKDAY` | `0` | День недельного отчёта: от `0` — понедельник до `6` — воскресенье |
| `REPORT_HOUR` | `9` | Час недельного отчёта, от `0` до `23` |
| `SECRET_KEY` | Производный от `BOT_TOKEN` | Секрет для HMAC кодов анонимных обращений |

`DATABASE_URL` вида `postgres://…` или `postgresql://…` автоматически приводится к формату драйвера `postgresql+asyncpg://…`.

Для **новой установки** рекомендуется задать отдельный постоянный `SECRET_KEY`. Сгенерировать значение:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

**На существующей установке не меняйте ключ произвольно.** Смена эффективного `SECRET_KEY`, включая добавление нового ключа вместо прежнего производного, делает старые коды анонимных обращений недействительными. Если отдельный ключ не задан, смена `BOT_TOKEN` также меняет эффективный секрет. При обычном обновлении сохраняйте прежнюю конфигурацию.

Токены, ключи и адрес БД с паролем не должны попадать в README, коммиты или публичные сообщения. `.env` исключён из Git и Docker build context. Настройки: [config.py](bot/config.py).

<a id="mentors"></a>
## Быстрое управление менторами

### Одной командой

Пользователи должны уже существовать в `users`: обычный способ регистрации — отправить боту `/start`. Поиск по username выполняется в базе бота, а не в глобальном каталоге Telegram.

Координатор или руководитель отправляет весь список:

```text
/addmentor
@mentor_one
@mentor_two
123456789
```

Допустимы Telegram ID, usernames и ссылки `t.me`. Разделители: пробелы, переносы строк, запятые и точки с запятой. Регистр usernames не важен.

Бот возвращает число добавленных, уже существующих, ненайденных и некорректных записей. При нескольких совпадениях username требуется уточнить Telegram ID. Повторы пропускаются; для массовой операции выдаётся полный файл `mentors_result.txt`.

### Файлом

Создайте `.txt` в UTF-8 со списком и отправьте его документом с подписью:

```text
/addmentor
```

Также можно ответить этой командой на сообщение с файлом. Лимит одной операции — **1000 записей**, размер файла — **128 КиБ**. Для большего списка разбейте импорт на несколько частей.

Массовое изменение не рассылает отдельное уведомление каждому участнику. Одиночное изменение уведомляет пользователя. Для обновления кнопок меню ментор может снова отправить `/start`.

Удаление использует тот же формат:

```text
/delmentor @mentor_one @mentor_two
```

Команда снимает членство в `mentors`, а не удаляет пользователя. Активные назначения тикетов бывшего ментора возвращаются в общую очередь, кроме случаев сохранения административных прав. История остаётся. Если у него есть будущие занятия, координатору нужно назначить другого ведущего; пока ведущий не имеет членства в `mentors`, новые записи на такие занятия недоступны.

### Через PostgreSQL

После запуска новой версии можно использовать [sql/bulk_add_mentors.sql](sql/bulk_add_mentors.sql). Замените примеры в `VALUES` своими usernames. Скрипт принимает `@` и разный регистр, пропускает повторы, показывает ненайденные и неоднозначные записи. Он не меняет `users.role` и не отправляет сообщения в Telegram.

Проверить текущий список:

```sql
SELECT u.telegram_id, u.display_name, u.username
FROM mentors AS m
JOIN users AS u ON u.telegram_id = m.telegram_id
ORDER BY u.display_name, u.telegram_id;
```

Для удаления предпочтительна `/delmentor`: она выполняет связанные действия с назначениями тикетов, которые простой `DELETE` из `mentors` не повторяет.

Подробнее: [MENTOR_IMPORT_GUIDE.md](MENTOR_IMPORT_GUIDE.md). Реализация: [mentor_refs.py](bot/mentor_refs.py), [staff.py](bot/handlers/staff.py), [repo.py](bot/repo.py).

<a id="notifications"></a>
## Уведомления о новых тикетах

Речь об обращениях `/feedback`, а не о входных билетах на занятия.

| Событие | Кому отправляется уведомление |
|---|---|
| Обычный новый тикет | Координаторам и, при `LEAD_GETS_ALL=true`, руководителям |
| Серьёзное обращение без ограничения доступа | Координаторам и руководителям независимо от `LEAD_GETS_ALL` |
| Тикет «про координатора» | Только руководителям |
| Благодарность выбранному действующему ментору | Ментору и администрации по правилам маршрутизации; тикет сразу закрывается |
| Назначение обращения ментору | Назначенному ментору; общая очередь всем менторам не рассылается |

При отсутствии координаторов обычные новые тикеты направляются руководству. Жалобы на координатора **не перенаправляются координаторам** даже при пустом `LEAD_IDS`. Выбор имени ментора в жалобе сам по себе не уведомляет его о жалобе.

### Проверка доставки

Каждый сотрудник открывает личный чат, отправляет `/start`, затем:

```text
/testnotify
```

Команда отправляет тест только вызвавшему её сотруднику, показывает роль и правила получения тикетов. После успешного теста повторно ставит в очередь его недоставленные уведомления о новых тикетах. Уже доставленные сообщения не пересылаются; фиктивный тикет не создаётся.

**Для личной переписки пользователь должен сначала начать диалог с ботом.** Это ограничение [Telegram](https://core.telegram.org/bots#how-are-bots-different-from-users). Сообщение в чате и системное всплывающее уведомление — разные вещи: бот не может принудительно включить звук и баннеры на устройстве.

### Очередь и повторные попытки

Тикет и задания доставки создаются в одной транзакции. После сохранения выполняется немедленная попытка отправки; дополнительный цикл проверяет `ticket_notifications` каждые 10 секунд. Временные ошибки повторяются с увеличением задержки от 30 секунд до одного часа; для ограничения частоты учитывается ответ Telegram.

Права получателя проверяются перед повторной отправкой. Блокировка бота или неверный адрес получателя переводит задание в `failed`; после устранения причины сотрудник может использовать `/testnotify`.

Это **не гарантия доставки ровно один раз**: при потере ответа Telegram после принятия сообщения повторная попытка может создать дубликат. `sent` означает успешный ответ API, а не прочтение человеком. Старые исторические тикеты не рассылаются задним числом. Очередь этой версии относится к уведомлениям о **новых** тикетах, а не автоматически ко всем сообщениям бота.

Контроль первого ответа настроен в [config.py](bot/config.py): серьёзное обращение — 4 часа, вопрос — 24 часа, жалоба и предложение — 48 часов; для благодарности срок не задан. Проверка просрочек выполняется отдельно от доставки новых тикетов.

Подробнее: [TICKET_NOTIFICATIONS_GUIDE.md](TICKET_NOTIFICATIONS_GUIDE.md). Код: [ticket_notifications.py](bot/ticket_notifications.py), [notify.py](bot/notify.py), [reports.py](bot/reports.py).

<a id="local"></a>
## Локальный запуск

Нужны Python 3.12, доступная база PostgreSQL и отдельный тестовый Telegram-бот. Зависимости зафиксированы в [requirements.txt](requirements.txt): `aiogram==3.31.0`, `SQLAlchemy[asyncio]==2.0.54`, `asyncpg==0.31.0`; также устанавливается `tzdata`.

Не используйте рабочую БД для экспериментов и не запускайте второй polling-процесс с рабочим токеном.

### Linux / macOS — Bash

Из корня проекта:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp env.example .env
```

Заполните `.env`: укажите токен тестового бота, реальный адрес локальной PostgreSQL, ID сотрудников и остальные нужные настройки. Ссылка `${{Postgres.DATABASE_URL}}` предназначена для Railway; локально нужен готовый URL.

Загрузите переменные в текущую оболочку и запустите бота:

```bash
set -a
source .env
set +a
python -m bot
```

В этой инструкции `.env` читается как Bash-файл: используйте собственный файл и заключайте значения со специальными символами в одинарные кавычки.

### Windows — PowerShell

Из корня проекта, без обязательной активации виртуального окружения:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

$env:BOT_TOKEN = 'YOUR_TEST_BOT_TOKEN'
$env:DATABASE_URL = 'postgresql://user:password@localhost:5432/hard_mentor_dev'
$env:COORDINATOR_IDS = '111111111'
$env:LEAD_IDS = '222222222'
$env:TIMEZONE = 'Asia/Almaty'

.\.venv\Scripts\python.exe -m bot
```

Примерные значения замените своими. Эти переменные действуют в текущем процессе PowerShell. Простое создание `.env` без загрузки не передаёт настройки боту.

### Docker

```bash
docker build -t hard-mentor-bot .
docker run --rm --name hard-mentor-bot --env-file .env hard-mentor-bot
```

В `.env` для Docker используйте строки `KEY=value` без `export` и без оболочечных кавычек вокруг значений. Укажите адрес PostgreSQL, доступный **из контейнера**: `localhost` внутри него не обозначает автоматически базу на компьютере. Образ проекта не запускает PostgreSQL; база настраивается отдельно. Файл `docker-compose.yml` в проект не включён.

### Ручная проверка перед рабочим обновлением

На тестовом боте и отдельной БД проверьте три сценария:

1. **Роли:** `/start` от участников → массовый `/addmentor` → `/mentors` → проверка доступа ментора и администратора.
2. **Занятие:** чек-лист и рекап-гайд → создание координатором → запись студента → вопрос и ответы → сводка ментора → посещаемость и материалы после занятия.
3. **Тикеты:** `/testnotify` у сотрудников → обычное обращение → проверка получателей → анонимное обращение по коду → жалоба на координатора с проверкой доступа только у руководства.

<a id="limitations"></a>
## Конфиденциальность и ограничения

**Личный чат.** Middleware игнорирует групповые чаты. Работа с обращениями и занятиями рассчитана на личную переписку с ботом.

**Анонимные тикеты.** В строке анонимного тикета не сохраняются `submitter_id` и `submitter_name`; время создания округляется до часа. Для доступа используется секретный код, в БД хранится его HMAC. Это не делает пользователя невидимым Telegram и не исключает узнавание автора по тексту, вложениям или обстоятельствам. Код доступа нужно хранить как секрет.

**Входные билеты.** Записи на занятия, вопросы и ответы на чек-листы связаны со студентом. Их видят назначенный ментор и администрация. Доступ к рабочей БД и инфраструктуре должен быть ограничен доверенной командой.

**Состояние диалогов.** Незавершённые пошаговые формы и дневные лимиты находятся в памяти процесса. После перезапуска форму может потребоваться начать заново, а счётчики лимитов сбрасываются. Уже сохранённые тикеты, записи, ответы чек-листов и задания доставки остаются в БД. Входящие обновления, которые бот ещё не получил, Telegram хранит не более 24 часов — длительный простой не покрывается безусловной гарантией сохранности сообщений ([Bot API](https://core.telegram.org/bots/api#getting-updates)).

**Языки и интеграции.** Обращения и часть общего интерфейса поддерживают русский и английский; раздел менторок сейчас преимущественно русскоязычный. Казахский перевод, внешняя календарная синхронизация, веб-панель и автоматическая годовая архивация в этой версии не реализованы. Банк фильтруется по предметам и темам; бот не выполняет полнотекстовый поиск внутри PDF/DOCX и не генерирует рекап-гайды с помощью ИИ.

<a id="troubleshooting"></a>
## Частые проблемы

| Проблема | Что проверить |
|---|---|
| Бот сообщает, что `BOT_TOKEN` или `DATABASE_URL` не заданы | Переменные именно сервиса бота; применение Deploy; локальную загрузку переменных |
| `/addmentor` не находит человека | Отправил ли он `/start` этому боту; актуальность username; числовой ID через `/myid` |
| В `users.role` у всех `mentee` | Это совместимая старая колонка. Смотрите `mentors`, `COORDINATOR_IDS` и `LEAD_IDS` |
| После назначения не видны нужные кнопки | `/start`; для ментора административные команды по-прежнему недоступны |
| Не приходят новые тикеты | `/testnotify`, правильные ID, отсутствие блокировки бота, `LEAD_GETS_ALL`, состояние очереди |
| В чате есть сообщение, но нет баннера или звука | Настройки уведомлений чата, Telegram и устройства |
| `TelegramConflictError` | Другой процесс с тем же токеном, лишнюю реплику или пересечение запусков |
| Нет занятий в расписании | Создал ли координатор будущее занятие через `/newsession` и действует ли роль назначенного ментора |
| Нельзя записаться на занятие | Не началось ли оно, не отменено ли, есть ли ведущий в `mentors` |
| После перезапуска пропал шаг анкеты | Диалоги в памяти; начать заполнение заново. Сохранённые записи проверить через `/status` или `/mysessions` |
| Бот не отвечает в группе | Использовать личный чат — это предусмотренное поведение |

Для диагностики доставки без чтения текстов обращений:

```sql
SELECT ticket_id, recipient_id, status, attempts, last_error
FROM ticket_notifications
ORDER BY id DESC
LIMIT 50;
```

`pending` — ожидает отправки, `sending` — зарезервировано обработчиком, `sent` — принято API, `failed` — отправка остановлена из-за ошибки, `skipped` — задание больше не применимо. `recipient_id = 0` — служебная запись для тикета без настроенных получателей, а не реальный Telegram-адрес.

Не публикуйте сырые логи, токены и выгрузки с персональными данными при обращении за помощью.
